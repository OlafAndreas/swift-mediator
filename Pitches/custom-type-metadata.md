## Summary of changes

Adds a marker attribute that lets a library enumerate the types annotated with it at run time, and the standard library function it is built on, which returns the contents of any custom `@section` from every loaded image that contains Swift code, backed by the compiler-emitted section index SE-0492 described.

## Motivation

Swift has no way for a library to find the types that opted into it. The pattern is everywhere, and every live example works around the gap in one of three ways.

**A hand-maintained list.** Swift Argument Parser's `CommandConfiguration` takes `subcommands: [ParsableCommand.Type]`, and adding a command means adding it to the array. Vapor's `RouteCollection`s are registered one by one. Each list is a place where a new type is forgotten, and each one forces the app to know every module's types.

**A code generation step.** SwiftLint's `BuiltInRules.swift` opens with `GENERATED FILE. DO NOT EDIT!` and lists 254 rule types; it is regenerated by `swiftlint-dev rules register` whenever a rule is added. XCTest on Linux needed a hand-written `LinuxMain.swift` for years. SwiftPM's first remedy, `swift test --generate-linuxmain`, had to be run on macOS; Swift 5.4 replaced it with automatic discovery built on the compiler's index data. Generation works inside one build, and not for a type that arrives in a plugin or a dependency.

**The Objective-C runtime, where it exists.** Quick finds every `QuickSpec` subclass with `allSubclasses(ofType:)`, which walks the Objective-C class list. Its own source notes that on Linux this is impossible and specs must be listed in `LinuxMain.swift` and `QCKMain`. Swift Testing is the one library that found a general answer, and on ELF it needed the Swift runtime to carry its section's bounds; on Wasm it uses the linker's encapsulation symbols, and on Mach-O and Windows it reads image headers itself.

Swift lets a module put constant data into a binary for a library to find later, but gives the library no portable way to find it. SE-0492 made the writing side a language feature and stopped at the reading side. This proposal is the reading side, at the two levels where libraries need it.

**Part I** teaches the runtime to find any custom section by name across every image it knows about and exposes that as one standard library function. The compiler emits the section index SE-0492 described for ELF, and emits it on Wasm and COFF too; the runtime registers it, and `customSectionContents(named:)` returns the named section's contents from every image, on every deployment target the toolchain supports. Libraries with their own record formats read their sections with it instead of walking images themselves.

**Part II** uses Part I for the case nearly every library has: a type declared as a custom attribute, applied to types in any module, and queried at runtime for every type that carries it. The compiler emits a constant record per application into a section the runtime owns, and no user code runs at load time. The attribute takes no arguments in this version; constant arguments are a future direction the record already leaves room for.

The two parts are one request made at two levels: let a library enumerate what other modules compiled in for it. Part I is the mechanism and stands on its own; it can proceed to review alone. Part II is its first client and the form most libraries will use, and it depends on Part I only in implementation. They are pitched together because they are one request and share one runtime walk, and the author expects a review manager may choose to review them as separate proposals.

Part II is a narrowed revision of SE-0385. That proposal was returned in 2023 with the Language Workgroup agreeing with its motivation and asking for a design built on macros and constant initialization. Both now exist. This proposal keeps SE-0385's attribute-as-type shape, replaces runtime-constructed attribute values with a constant record the compiler writes, limits applications to types, leaves out attribute arguments, and uses the constant-record machinery that SE-0492 added in Swift 6.3.

### What the Language Workgroup agreed with

SE-0385 proposed custom attributes whose applications could be enumerated at runtime. The [return notice](https://forums.swift.org/t/returned-for-revision-se-0385-custom-reflection-metadata/63758) said the Workgroup "agrees with the motivation and general direction of the proposal" and that the use cases "sufficiently motivate inclusion in the language". It asked for a revision addressing three points:

1. The `init(attachedTo:)` overload scheme hard-coded which declaration kinds could carry metadata, could not express generics or extensions, and lost information for functions. The notice suggested macros as "a better mechanism for creating metadata for a specific declaration".
2. Discovery ran generator functions to produce attribute values, which "precludes static extraction of custom metadata, such as a tool that extracts the set of available tests from a binary". The notice asked for a design that considers "the interaction with constant initialization".
3. The query API depended on a reflection library whose direction was unsettled.

Since then, attached macros shipped, and SE-0492 made constant initialization into named sections a language feature. Swift Testing combined the two: a macro emits a constant record into `swift5_tests`, and tests are found on every platform without a registry, with the runtime carrying that section's bounds on ELF, the linker's encapsulation symbols supplying them on Wasm, and Swift Testing reading image headers itself on Mach-O and Windows. The runtime still carries a `swift5_runtime_attributes` section range in `MetadataSections` from the SE-0385 implementation; the compiler side was removed and nothing fills it.

### What libraries do today, and what it costs

Since Swift 6.3 a library can build this itself. The author of this pitch did, in three packages, to measure the cost. The macro side works: `@Handler` on a struct expands to a `@section @used` global holding a record, and the mediator finds every handler at startup with no registration code. Everything below the macro is where the cost lands:

* A `@section` global must be a constant expression, so a record cannot hold a string, and in practice not a metatype either: SE-0492 lists non-generic metatypes among constant values, but the Swift 6.4 compiler rejects `Foo.self` in a `@section` constant with "'@const' value should be initialized with a compile-time value". The record therefore holds `@convention(c)` closures that return a metatype erased to a raw pointer, which also forces it out of read-only memory. Each library invents its own tuple layout. In the SE-0492 pitch discussion Joe Groff [noted](https://forums.swift.org/t/77435/15) that Swift guarantees no general struct layout and advised primitive, tuple and `InlineArray` types for externally parsed data.
* An attached macro cannot add attributes to the declaration it is attached to, so a language attribute would have to be written by hand next to every framework macro. A peer macro at global scope cannot introduce arbitrary names, so it emits a fixed set of named globals per declaration. Several keys on one type become a tuple of records packed into one of them.
* Reading the section back is a per-platform walker. On Mach-O, enumerate images and call `getsectiondata`. On ELF, section headers are not mapped; a library either references linker-synthesised `__start_`/`__stop_` symbols, which only cover its own image, or re-reads every loaded image's section headers from its file on disk through `dl_iterate_phdr`. On Windows, parse PE headers in memory. Swift Testing's walker, `SectionBounds.swift`, is 358 lines, and it has the advantage that the runtime registers its section on ELF. No other library gets that.
* The Swift 6.4 toolchain does not emit the `swift5_sections` index SE-0492 described for ELF, so the file re-read is the only generic option today. It fails for images whose file was replaced or removed after loading.

Every library that wants discovery pays all of this, or depends on a package that does. The gap is widest off Apple platforms, where image headers are not mapped or there is no path at all, and the design starts there. The compiler and runtime already solve each of these problems for Swift's own metadata. They can emit a stable record, keep it alive, place it in a section they own, register that section on every object format, and enumerate it. This proposal asks them to open the enumeration itself to libraries that have their own records, and to do the whole job for one more record kind so that most libraries never need their own. On ELF the runtime today carries bounds only for its own sections, so it is the one object format where every library, Swift Testing included, still lacks a general way to find other images' sections.

## Proposed solution

### Part I: reading any custom section

A library that already has its own record format, placed with SE-0492's `@section`, keeps it and drops its walker. The runtime can find any custom section in every image it knows about, which is every image that contains Swift code, and one function returns the contents:

```swift
#if objectFormat(ELF) || objectFormat(Wasm)
let pluginSection: StaticString = "myplugins"
#elseif objectFormat(COFF)
let pluginSection: StaticString = ".myplugs$B"
#elseif objectFormat(MachO)
let pluginSection: StaticString = "__DATA_CONST,__myplugins"
#endif

for section in customSectionContents(named: pluginSection) {
    for record in section.bindMemory(to: PluginRecord.self) {
        register(record)
    }
}
```

The section name is written as in the `@section` attribute, under the same `#if objectFormat` conditions, so a library that can place a record can also read it back; on COFF the runtime strips the `$` group suffix, since the linked image's header holds `.myplugs`. The result is one buffer per image that contains the section, and each buffer stays valid as long as its image stays loaded; the Swift runtime does not support unloading images that contain Swift code, so in practice that is the life of the process. This is the "cross-platform section access API" that SE-0492 left as a future direction, in the shape its text sketched.

This is enough for a library that is willing to design a record format and keep it stable. Most are not, and should not have to be. Part II removes that work for the common case.

### Part II: a typed attribute for types

A library declares a key. The key is a type marked with a new built-in attribute, and it becomes usable as a custom attribute. Its only role is identity: it takes no arguments in this version. The names `@customMetadata`, `CustomMetadata` and `customSectionContents` are placeholders. Modelled on a linter's rule registry:

```swift
// In the linter's core module
@customMetadata
public enum LintRule {}
```

Rule authors apply it to their types, directly or through an extension. Rules may live in the linter's own modules or in a third-party rule package:

```swift
@LintRule
struct ArrayInitRule: Rule { ... }

// Equivalent, and what a framework's extension macro would emit:
@LintRule extension TrailingWhitespaceRule {}
```

The linter asks the runtime for the types, and the generated 254-entry list is gone:

```swift
for case let ruleType as any Rule.Type in CustomMetadata.types(marked: LintRule.self) {
    registry.register(ruleType)
}
```

Everything the linter knows about a rule beyond its existence, its identifier, whether it is opt-in, whether it can correct, stays where it is today: static properties and protocol conformances on the rule type, read after discovery. Attribute arguments that would carry such facts in the record are a future direction; Alternatives explains why this version leaves them out.

The compiler emits one constant record per application, holding references to the type's and the key's context descriptors. The runtime owns the record layout and the section name on every object format, keeps records alive, and returns resolved metatypes on request. Nothing runs at load time. The query is Part I's enumeration over a section the runtime names, followed by resolving each record to a type; the attribute adds a record format the compiler and tools understand, and takes the format design away from the library. It is also what a macro cannot do with today's compiler: SE-0492 admits non-generic metatypes as constant values, but the shipping compiler rejects one in a `@section` global, so a macro cannot yet emit a constant reference to a type. Alternatives considers finishing that part of SE-0492 instead, and why it would not replace the attribute.

On Apple platforms the query requires the OS release whose runtime ships it. The record is resolvable through the stable ABI alone, so a back-deployed fallback is possible, and the design keeps that option open without promising it. On Linux and Windows the runtime ships with the toolchain, so no back-deployment question arises.

Who may apply a key follows the key type's access level, with no new rules. An `internal` key can only be applied inside its own module, which lets a library drive the feature from its own macros without exposing the hook to consumers. A `public` key can be applied anywhere, including to types the applier does not own. A type's owner can refuse a specific key with an unavailable extension, the hatch SE-0385 defined.

The extension form is what lets frameworks hide the attribute behind their own macro. A `@SwiftSyntaxRule`-style macro that today would have to tell its users to also write the key attribute can instead emit `@LintRule extension TrailingWhitespaceRule {}` as an extension macro. The author's swift-mediator prototype works this way: its `@Handler` macro emits a raw tuple global today and would emit the extension instead, with no change for adopters.

## Detailed design

### Part I: custom section access

**Index emission.** The compiler emits the `swift5_sections` index as SE-0492 sketched it, with one change to the entry layout described under ABI compatibility: one `linkonce_odr` entry per custom section that holds a variable of the compilation, each naming the section and its start and stop addresses as 32-bit self-relative offsets, each in its own COMDAT group so that one entry per section survives linking. SE-0492 limited the index to ELF and said that registering it and exposing an API "is left as a future direction". This proposal is that future direction, and extends the index to COFF and Wasm, the other two formats where the runtime's per-image stub `swiftrt.o` is linked into every image. On ELF and Wasm the bounds are the `__start_`/`__stop_` symbols the linker defines for any output section whose name is a C identifier. Referencing them does not keep the section alive: lld by default, and wasm-ld always, discard a section that nothing else references, and the symbols would then be undefined and the link would fail. So the compiler also emits a zero-length, retained anchor into each indexed section, in its own COMDAT group. The anchor keeps the output section, and so its bounds, in existence while records without `@used` stay collectable; the runtime stub does the same for the runtime's own sections with an empty retained section directive. COFF defines no such symbols, but its linker merges `name$X` input sections into `name` ordered by `X`, so the compiler brackets a section's records itself: a 16-byte start marker in the section's `$A` group, aligned so that records of any Swift alignment follow it directly and carrying its own size in its first word so the runtime can step over it, and a stop marker in `$Z`. Records must therefore live in a `$` group that sorts between the two, and the entry names the section by the part before the `$`, which also sidesteps the PE format's eight-character limit on section names in linked images. Mach-O needs no index: section bounds are in every image's header and can be looked up by name.

The compiler emits an entry only for a variable definition it places in a section, and never for a declaration it merely references from another module, so an image never claims a section it does not contain. Functions are not indexed: SE-0492 as accepted places only data, Wasm's linker defines encapsulation symbols only for data segments, and on COFF code placed in a custom section lands in a separate output section outside the markers. Because the fields are relative, the index is read-only, needs no load-time relocation, and can be read from the file by a tool that knows the section's file offset. Where a linker does not fold the COMDAT groups, as wasm-ld does not for retained data, an image can hold several entries for one name; they describe the same bounds, and the runtime takes the first. A name the index cannot describe gets a warning and no entry; see Diagnostics. Embedded Swift emits no index: its sections are placed for linker scripts and bare-metal images that have no runtime to read one. The index itself lives in a section the runtime owns:

| Object format | Index section |
|---|---|
| ELF, Wasm | `swift5_sections` |
| COFF | `.sw5sect$B`, between the stub's own `$A` and `$C` markers |
| Mach-O | none |

**Registration.** The ELF, COFF and Wasm stubs already construct a `MetadataSections` for their image and pass it to `swift_addNewDSOImage`. The struct gains a final `swift5_sections` range covering the index, which each stub fills from its linker-defined bounds, and `CurrentSectionMetadataVersion` moves from 5 to 6. The runtime reads the new field only when an image's `version` is at least 6, as Swift Testing already does before reading `swift5_tests`; an older stub against a newer runtime keeps working, and a newer stub against an older runtime registers everything but the index. On Mach-O the runtime registers one more dyld load callback, on first query, that records each image's header in an append-only list. dyld reports every image already loaded before the registration returns and every later load as it happens, so the list is complete from the first call. The callback runs under dyld's locks like the runtime's existing ones and does nothing but append. Nothing is scanned at load time: a query scans the recorded headers for the requested name with `getsectiondata`. Which images are recorded depends on the callback the runtime could register: the Objective-C runtime's reports images that carry Objective-C image info, which every Swift image does, while dyld's reports every image.

**API.**

```swift
/// The contents of the custom section named `name` in every image the Swift runtime
/// knows about that contains one. One buffer per image, covering the records in that
/// image's section. Unordered. A snapshot of the images loaded at the time of the call.
@backDeployed(before: SwiftStdlib X)  // the release that adds the runtime entry point
public func customSectionContents(named name: StaticString) -> [UnsafeRawBufferPointer]
```

`name` is the section name as written in `@section` for the current object format. The images searched are the ones the runtime knows: on ELF, COFF and Wasm every image whose stub registered with it, which is every image that contains Swift code; on Mach-O every image the loader reported, which can include images without Swift code. The contract is therefore sections placed by Swift code, and a section placed by C in a C-only library is found on Mach-O and not elsewhere. Each buffer stays valid as long as its image stays loaded; the Swift runtime does not support unloading images that contain Swift code, and its own image registry is append-only for the same reason. There is no observation API: a caller that loads a plugin with `dlopen` calls again, as with the typed query. Linux, Windows and Wasm ship the runtime with the toolchain and need none of what follows in this paragraph; Apple platforms are the one place where the runtime is part of the OS, and it exists for them. The function is back-deployed. Where the runtime has the entry point described below, the function calls it; on an Apple OS release whose runtime predates it, the copy of the function emitted into the client walks dyld's image list and reads each header with `getsectiondata`, as Swift Testing does today, so the function works on every deployment target the toolchain supports. It is a free function rather than a member of a new namespace type because a new type cannot be back-deployed: its metadata would be missing from older runtimes, while a function's body can be emitted into clients. The standard library's memory primitives are free functions too, and `withUnsafeTemporaryAllocation` is emitted into clients for the same reason. The return type is `UnsafeRawBufferPointer` rather than `RawSpan` and the name a `StaticString` so that the function depends on no type newer than the ABI; a `RawSpan` form is a future direction. A static string's pointer form is already a NUL-terminated C string, so the call allocates nothing beyond its result.

The function is a thin wrapper over one runtime entry point, `swift_enumerateCustomSections(name, body, context)`: a C function taking the name and a callback invoked once per image that contains the section. A library that cannot take on the standard library's availability can call it directly, as Swift Testing calls `swift_enumerateAllMetadataSections` today.

Records inside the buffers are the caller's own format. Alignment, record size and validity are the caller's responsibility, exactly as they are today for a library reading its own `__start_`/`__stop_` range.

#### Prototype

Part I is implemented in the draft pull request linked in the header. It builds with compiler assertions on, on macOS and on Linux. On both, the IRGen tests and the runtime round trip pass; on Linux the Sema test for the naming rules passes as well, and the linked test binary, produced by GNU ld, carries one index entry per section with its bounds defined. A second Linux test links with lld and `--gc-sections`, with a record that nothing references, and checks that the link succeeds and the kept record is found; without the anchor that link fails with an undefined `__start_` symbol. COFF and Wasm emission were checked by cross-compiling modules and linking them with lld and wasm-ld: one index entry per section survives COMDAT folding on COFF, the entry's offsets resolve to the two markers, the start marker, the records and the stop marker land in one read-only section in that order, and on Wasm the bounds are defined with records present, with every record dead-stripped, and across two object files. On macOS a client built against the new standard library runs correctly against both the new runtime and the shipping OS runtime, which lacks the entry point, so the back-deployed path has been exercised. The branch also fixes a pre-existing compiler assertion that one of the new tests exposed: a file referencing a `@used` variable defined in another file of its module listed the declaration in `llvm.used`. Nothing has run on a Windows host; the Sema test for COFF names is written for that host and remains unexecuted.

As a consumer, swift-discovery was rebuilt on the new function. Removing swift-sections and calling `customSectionContents(named:)` is a ten-line change, after which all fifteen of its tests pass on macOS on both runtimes, and its library and a discovery program run on Linux against the new runtime. The 315-line per-platform walker it depended on is gone and the typed layer above it is unchanged. That change is on the swift-discovery branch linked in the header.

### Part II: custom metadata attributes for types

#### Declaring a metadata attribute

`@customMetadata` may be applied to a struct or enum that is non-generic and declared at module scope or nested in a non-generic type.

The key is never instantiated by the feature and its layout plays no part, so it may have stored properties, cases, methods and computed properties, and it may be resilient; none of that is read. Its only role is to give applications an identity through a context descriptor the record can reference. A caseless enum is the natural spelling.

Keys with arguments, whose stored properties would be filled from constant arguments at the application site and handed back by the query, are a future direction. The record reserves a field for the value so that adding them later changes no layout.

#### Applying a metadata attribute

A metadata attribute may be applied to:

* the primary declaration of a non-generic struct, enum, class or actor declared in Swift, that is not local and not nested in a generic type;
* an unconstrained extension of such a type.

Types imported from C or Objective-C are excluded: the record references a Swift context descriptor, which they do not have.

The application names the key type and nothing else. No initializer is called and none needs to be visible, so a `public` key with no accessible initializer still works across modules.

Applicability follows the key type's access level, exactly as referencing the type would:

| Key declared | May be applied from |
|---|---|
| `private`, `fileprivate` | the same file |
| `internal` | the same module |
| `package` | the same package |
| `public` | any module |

Each application emits one record in the module containing the application. Applying the same key to the same type twice within one module is an error. The same key applied to the same type from two different modules produces two records, and the query returns the type once. SE-0385 forbade applying the attribute outside the type's module; Alternatives explains why this proposal allows it. A type's author may forbid a specific public key on their type with an unavailable extension in the type's own module:

```swift
@available(*, unavailable)
@LintRule extension RuleTestHelper {}
```

An application of that key to `RuleTestHelper` anywhere else is then an error. The opt-out travels with the type: it is serialized into the module's binary module and interface so that an application in another module can be rejected. This is the opt-out SE-0385 specified; it requires the owner to know the key. A general marker forbidding all metadata attributes on a type is a future direction.

The restrictions on the attributed type mirror what SE-0492 enforces for `@section` globals and what SE-0385 required for discoverable declarations: generic and local declarations cannot carry a constant record, and generic types cannot be represented as a single metatype at runtime.

#### The record

Each application compiles to a fixed-size record in a section owned by the runtime:

```c
struct CustomMetadataRecord {
  RelativeIndirectablePointer<ContextDescriptor> type;       // the attributed type
  RelativeIndirectablePointer<ContextDescriptor> attribute;  // the key type
  RelativeDirectPointer<const void> value;                   // reserved for attribute arguments; null
  uint32_t flags;                                            // see below
  uint32_t availability;                                     // see below
};
```

The two descriptor references are indirectable so that a record can refer to a type or key defined in another image. Relative pointers keep the section position-independent and readable from the file on disk, so a tool can list the attributed types of a binary without running it. That addresses the second point of the SE-0385 return notice. No function pointers are stored. Metadata is obtained through the descriptor's accessor only when a query asks for it.

The record must stay resolvable from client code without private runtime entry points. Everything a reader needs is in the record itself or reachable through the stable ABI: the section bytes, the relative pointers, the context descriptor and its access function. This is what makes a back-deployed fallback of the query possible on Apple platforms, and an implementation should not trade it away for a smaller record.

`value` is null in this version. It is reserved for the future direction that admits constant arguments on the key, so that adding them changes what the field points to and not the record layout; a runtime of this version ignores it.

`flags` is reserved and zero in this version. `availability` is the attributed type's minimum OS version for the platform the module was built for, packed as major, minor and patch, or zero when the type is no less available than the module's deployment target. The compiler already computes this for `@available` checking, and context descriptors carry no availability today, so the record does. The requirement is that the runtime can decide availability without running user code.

Records are retained the way protocol conformance records are retained. Adopters do not write `@used`. The same caveat applies as for conformances and for SE-0492: a static archive member that nothing references is not linked, and its records go with it.

#### Sections and registration

The compiler places records into one section per object format, named by the compiler:

| Object format | Section |
|---|---|
| ELF, Wasm | `swift5_runtime_attributes` |
| COFF | `.sw5ratt$B` |
| Mach-O | `__TEXT,__swift5_rattrs` |

`MetadataSections` already has a `swift5_runtime_attributes` field, and the ELF, COFF and Wasm `swiftrt.o` stubs already declare and register that section under the names above. The Mach-O name is new, and so is the lookup behind it: on Mach-O the runtime looks the section up by name in each image header that Part I's registration recorded, at query time. The compiler emits nothing into any of these sections today, so there is no legacy content to distinguish.

Because this section is owned by the runtime and registered by name, the typed query does not depend on the section index of Part I. The two parts share the enumeration code in the runtime, not a data dependency: Part I's lookup of an arbitrary name and Part II's lookup of this fixed name go through the same per-image walk.

#### The query

```swift
public enum CustomMetadata {
  /// Every currently loaded type that carries `key`. Unordered. Each type appears once.
  public static func types<K>(marked key: K.Type) -> [Any.Type]
}
```

The runtime walks the `swift5_runtime_attributes` range of every loaded image through Part I's enumeration, selects records whose `attribute` descriptor resolves to `K`, skips records whose availability excludes the running OS, resolves each `type` descriptor's metadata, and returns the types. Records are deduplicated by type metadata and key metadata, which collapses a static archive linked into two images and the same key applied from two modules. The result is a snapshot of the images loaded at the time of the call. A caller that loads a plugin with `dlopen` calls again. The name leaves room for a query that also returns argument values, should that future direction land.

Order is unspecified. Link order is not stable across platforms and build systems, so libraries that need an order read it from the discovered type, as a static requirement of a protocol it conforms to, and sort.

The query lives in the standard library and does not depend on a reflection module, which addresses the third point of the return notice.

#### Diagnostics

* `@customMetadata` on anything other than a non-generic struct or enum.
* A metadata attribute applied to a generic, local, or non-nominal declaration, or to a constrained extension.
* A metadata attribute whose key is not visible at the application site, reported as the ordinary access-control error.
* The same key applied to the same type twice in one module, or applied to a type whose module has forbidden it.
* Arguments passed to a metadata attribute, since this version takes none.
* A metadata attribute applied to a type imported from C or Objective-C.
* For Part I, a warning for a `@section` name the index cannot describe: on ELF and Wasm a name that is not a C identifier, on COFF a name without a `$` group that sorts between `$A` and `$Z`. The section still works; `customSectionContents(named:)` cannot find it. The warning is issued only for `@used` variables, the records meant to be found, and not in Embedded Swift. It belongs to the diagnostic group `SectionNotIndexable`, so `-Wwarning SectionNotIndexable` keeps it a warning under `-warnings-as-errors`; Swift has no flag that silences a group, so a section that is meant for a linker script and never for run-time lookup keeps the warning or drops `@used`.

### Embedded Swift

In Embedded Swift there is one statically linked image and no loader, and `@section` is how code places data for linker scripts and bare-metal images, where names such as `.init_array` are the point. Part I emits no index and no naming warning there: an index would be an orphan section with no reader, and a warning on every linker-script name would be noise. `customSectionContents(named:)` is unavailable in Embedded Swift; a non-allocating form that resolves a name against the image's own encapsulation symbols is a future direction. The prototype also returns nothing in a statically linked Mach-O image, which has no dyld to report headers. Part II is unavailable in Embedded Swift: the compiler emits no type metadata there, so neither the context descriptor the record points to nor the `Any.Type` the query returns exists. A metadata-free form that returns only key values is a future direction.

## Source compatibility

Additive. No existing code changes meaning. `@customMetadata` is a new attribute name; `hasAttribute(customMetadata)` lets libraries adopt conditionally. `customSectionContents(named:)` is a new standard library function. Existing `@section` variables gain index entries on ELF, COFF and Wasm with no change to their declarations, outside Embedded Swift. A `@used` variable whose `@section` name the index cannot describe gets a warning, not an error.

## ABI compatibility

Additive. One record layout in an already-reserved section, two new runtime entry points, one per part, and a new trailing field in `MetadataSections` with the version moved to 6, compatible in both directions as described under Registration. The `swift5_sections` entry layout departs from the sketch in SE-0492 in one way: its three fields are 32-bit offsets relative to their own address rather than absolute pointers. Nothing emits the sketch today, so there is no compatibility to preserve, and relative fields make the index read-only, free of load-time relocations, readable from the file, and consistent with every other `swift5_*` record. On COFF, the start marker's self-describing size is part of the contract between compiler and runtime, alongside the entry layout. The attribute record layout becomes ABI once shipped; `flags` and `value` are reserved so it can evolve. A key's layout is not part of the ABI, since the feature never reads it; a key is identified by its context descriptor, so renaming or moving it is the ABI change, as for any type.

## Implications on adoption

Applying the attribute requires a compiler that supports it. Records emitted into a binary are inert on a runtime that does not know the section, so a library can attribute its types and still deploy to older OS versions; only the query is unavailable there. On Apple platforms Part I's function is back-deployed and works on every deployment target the toolchain supports. Part II's query requires the OS release that ships the runtime support; the attribute itself works on every deployment target, since its records are inert on an older runtime. On Linux and Windows both queries follow the toolchain.

A library can adopt and un-adopt the attribute without affecting its source or ABI compatibility, since the attribute changes no symbol and no layout of the attributed type.

A key carries no arguments in this version. A rule identifier, a route path, a priority or a display name is read from the discovered type, as a static property or a protocol requirement, which is where SwiftLint's `RuleDescription` already lives. Arguments are a future direction, and when they come they will be bounded by SE-0492's constant rules, which exclude strings today.

Discovery scope is a library concern. When several independent modules share one binary, such as SwiftPM linking all test targets into a single test bundle, a library may want to restrict results to a module. The qualified name of a type gives its module; swift-discovery does this with a filter over the result and the runtime need not.

For libraries with existing `@section` records, adoption of `customSectionContents(named:)` replaces a per-platform walker with one call and no change to the records. On ELF this is the first way for such a library to see other images' sections without re-reading files from disk. A library that cannot adopt new standard library types in its discovery path, or must run on earlier Apple OS releases, is not ruled out: the function is back-deployed and uses no type newer than the ABI, and the runtime entry point beneath it needs no standard library availability at all.

## Future directions

* **Attribute arguments.** A key with stored properties of constant-expressible types, applied with labelled constant arguments and returned alongside the type by an `applications(of:)` query. The record's `value` field is reserved for it, and SE-0492's constant rules define what an argument may be; strings and metatypes would follow SE-0492's own growth. An earlier draft of this proposal included this, and Alternatives explains why it is deferred.
* **Uniqueness and existence constraints.** Once a key can take a metatype argument, a key could declare that argument `unique`, and a type or protocol could declare that it `requires` an application: the compiler would emit a strong symbol per application and an undefined reference per demand, so a duplicate or a missing application fails at link time within one link and is checked at run time across images, as `@main` already is for one fixed symbol. The author's mediator needs exactly one handler per request. A [branch](https://github.com/OlafAndreas/swift-mediator/tree/olaf/link-time-uniqueness) approximates the link-time half with today's macros, deriving the symbol from the spelled type name where the compiler would use the mangled one; its [design note](https://github.com/OlafAndreas/swift-mediator/blob/olaf/link-time-uniqueness/Documentation/LinkTimeUniqueness.md) records the behaviour with dynamic libraries on each object format and the open questions.
* **A general opt-out.** A marker on a type forbidding all metadata attributes from other modules, for owners who do not know which keys exist.
* **Functions and properties.** SE-0385's remaining scope. Function records would need a different shape, and the return notice's concerns about labels and generics would need answers.
* **Inference from protocols.** SE-0385 allowed a metadata attribute on a protocol to be inferred onto conforming types. This interacts with conformances declared in extensions and across modules, and is left out here.
* **Generic types.** Would need a query in the other direction, as SE-0385 noted.
* **A `RawSpan` form of `customSectionContents(named:)`.** Once availability allows, a safe view over the same memory.
* **Linker-set and plugin macros.** SE-0492 sketched `@LinkerSetEntry`-style macros over a section access API. With `customSectionContents(named:)` in the standard library those macros become possible as libraries, and the typed attribute covers the common case directly.
* **Part II in Embedded Swift.** Embedded Swift has no type metadata to return, so a query there would have to yield something else per application, and needs its own design.
* **Static tooling.** A `swift-demangle`-style tool listing the attributed types of a binary, which the record layout makes possible.

## Alternatives considered

### Revise SE-0385 as it stood

The three return-notice points still apply to that design. This proposal is the revision: attribute-as-type kept, `init(attachedTo:)` replaced by a constant record the compiler writes, scope cut to types, no arguments, no reflection-library dependency.

### Constant arguments on the key

An earlier draft let a key declare stored properties of constant-expressible types and be applied with labelled constant arguments, returned alongside the type. It is deferred, not rejected. It brings the whole of SE-0492's constant-expression rules into the attribute, which is the interaction the return notice asked to see considered and the part of SE-0492 still growing; it needs a layout contract for the key, a non-resilient struct with a whitelist of property types, and byte-wise deduplication of values across modules; and it is not what the libraries that exist use. The author's mediator, Quick-style discovery and SwiftLint's registry all need the set of types, and keep the facts about each type on the type. A marker gives static tools the set of attributed types, which is what the return notice named. The record keeps a null `value` field so that arguments can be added without a new layout.

### Restrict applications to the type's own module, as SE-0385 did

SE-0385 prohibited the attribute in extensions outside the type's module "to prevent the same type from having multiple reflection metadata annotations of the same type". This proposal keeps uniqueness within a module and defines the cross-module case instead, because the libraries that motivate it need to attribute types they do not own: a rule package wrapping types from another package, or an app registering a dependency's types as handlers. SE-0385's owner opt-out is retained, and a duplicate can only come from a second module.

### Enumerate protocol conformances instead

The runtime has conformance records but no public enumeration API, and its conformance lookup is indexed from a type to a protocol; a query from a protocol to all of its conformers would scan every conformance record in every image and materialize each candidate's metadata. Conformance is also not opt-in: every type conforming to `Rule` would be found whether or not it wanted to be, including test helpers, and a retroactive conformance in a third module would enrol a type its owner never offered. The Workgroup agreed with opt-in annotation as the direction. A conformance query could be a future direction.

### Emit the record as reflection metadata

SE-0385 called its records reflection metadata. In the compiler that term names the field, associated-type, builtin and capture descriptors, type references and reflection strings in the six sections `swift5_fieldmd`, `swift5_assocty`, `swift5_builtin`, `swift5_capture`, `swift5_typeref` and `swift5_reflstr`, which `Mirror`, the debugger and Remote Mirror read. They are optional by design: `-disable-reflection-metadata` omits them, `-reflection-metadata-for-debugger-only` emits them unretained and unreferenced from the type descriptor so the linker can drop them, and Embedded Swift emits none. A type's registration with a library cannot live in data that a build flag removes, so the record is emitted and retained like a protocol conformance record in every reflection mode. The reflection sections are also reached from the type, not enumerated: the runtime follows a pointer from a type's descriptor to its field descriptor and never walks the section in-process, while this query runs from a key to every type that carries it, across images. Placing the record in a reflection section would still need the per-key list and the image walk this proposal adds, under a name that implies it can be stripped. The attribute is not spelled `@reflectionMetadata`, SE-0385's final spelling, for the same reason: it does not use the reflection machinery and should not be expected to share its fate.

### Leave it to macros and `@section`

This is the status quo and the author's prototype. Its costs are listed under Motivation: per-library record layouts the runtime cannot read, function pointers standing in for metatypes, a fixed set of globals per declaration, a walker per platform, re-reading image files on ELF, and no Windows path until someone writes one. A library can do it; every library doing it is the problem.

### Finish SE-0492's metatype constants and leave the record to macros

SE-0492 admits non-generic metatypes as constant values, and the shipping compiler does not yet accept one in a `@section` global. Implementing that would let a macro emit a record that holds a constant reference to a type, which removes the function-pointer workaround from the status quo and is worth doing on its own. It would not remove the rest: each library would still define a record layout the runtime and tools cannot read; records emitted for one type by two modules would not be deduplicated; availability could not be checked without running user code; a peer macro cannot add an attribute to its host, so the extension form that lets a framework hide the key behind its own macro would still need a built-in attribute; and every library would still ship a walker or depend on Part I. The case for Part II rests on those five, not on the missing constant.

### Only the section access API

The author's first pitch, [Runtime enumeration of custom sections](https://forums.swift.org/t/pitch-runtime-enumeration-of-custom-sections/90011), proposed only this half. It solves the walker, which is one of the four costs under Motivation, and leaves the other three: every library still invents a record layout the runtime and tools cannot read, still stores function pointers where a metatype belongs, and still needs a hand-written attribute next to every framework macro. Feedback in that thread was to state the want rather than the mechanism; the typed attribute is the want.

### Only the typed attribute

Leaves out libraries whose records are not type metadata: test content, debugger summaries, linker sets, plugin tables. Those exist today on `@section` and have no portable way to be read across images on ELF. The runtime work to register and enumerate custom sections is the same work the typed query needs, so shipping the attribute without exposing the enumeration would duplicate the walker in every such library for no saving in the runtime.

### An observation API for newly loaded images

The first pitch included one. The runtime does not need it to serve queries, Swift Testing's current design does not use one, and the Apple-only library code it was modelled on has been removed from Swift Testing. Callers that load images at runtime call the query again.

### Reserve a kind in `swift5_tests`

Swift Testing's test content ABI reserves `kind` values for other testing libraries' test content, and its maintainers said in the [earlier thread](https://forums.swift.org/t/pitch-runtime-enumeration-of-custom-sections/90011/4) that the section's layout constraints are specific to test data.

### Build-time code generation

A SwiftPM plugin cannot see other modules, breaks under conditional compilation, and reintroduces the registry the feature exists to remove.
